# PC-ISSUE-172：AI 多轮任务状态丢失，导致确认后无法生成结构化提案

日期：2026-10-25 00:30 前后（用户提供的最后一轮真实聊天转录）
优先级：P1 功能阻断；若发现绕过显式审批直接正式发布，升级 P0。
状态：OPEN / 代码传播路径已核实；尚未执行修复后回归。
注意：这份记录只把 2026-10-25 凌晨最后一轮视为最新复现，之前几天的聊天属于历史版本迭代。

## 复现（避免纳入个人私人日程）

1. 用户要求：今天 01:45–02:45 创建多个相互重叠的事件，最初误说“重复事件”。
2. 用户修正：“我的意思是就创建多个就行了，不用重复”。
3. AI 提出 5 个重叠的单次事件，仍在上述 1 小时窗口内。
4. 用户先发“14514”，再确认“就叫这个”：5 个事件标题全部是 14514。
5. 用户回复“确认”。
6. 聊天 AI 正确复述上述信息，但自动结构化阶段报告：“模型未返回可操作的日程项；请明确要创建的标题、日期和时间”。

真实屏幕只能证明提案生成失败；未读取当时数据库，不能宣称一定未入库、也不能宣称存在越权发布。

**确定性重放锚点**：假设用户发起本轮请求时的可信手机本地时钟为 2026-10-25 00:30 Asia/Shanghai；目标窗口是 2026-10-25 01:45–02:45。不同真实设备时区应按各自当时的可信时钟解释，不可以在用户后来“确认”时重新解析“今天”。

**预期**：5 张不同身份、同名“14514”、单次而非周期重复（recurrence NONE）的 Activity 候选，各自起止落在窗口内，并有实际重叠。具体子时间段如未由用户指定则是模型建议，必须先展示可审查卡；未经卡片授权不得正式发布。名称相同不能被去重成一条。

## 已核实的源码根因（当时 HEAD 5c9cea0）

- AiClient.chat 通过 AiConversationWindow.select(history) 把有界多轮消息发送给聊天模型，所以聊天回答能够复述完整任务。
- AiChatActionParser.authoritativeCurrentUserSource(parsed, history.last().content) 把结构化输入限定为最后一条用户消息。这防止模型自行编造 source，是之前的安全修复，但对于“确认”“就叫这个”“不是重复”等多轮任务交接丢失了关键信息。
- PowerCalApp.submitAiChatInput 直接将 automaticProposalSource 交给 AiClient.interpret。
- AiClient.interpret 构造新的单轮结构化请求，没有带入之前多轮确认的任务快照。如果最后一条是“确认”，结构化解释器只拿到“确认”，自然可能输出空事件数组。
- AiResponseParser 对空事件数组回报缺少标题、日期和时间，因此产生与用户观测完全吻合的错误文案。

这是从源码可证实的信息传递缺口。尚不能仅凭聊天文本断言供应商最终返回的 JSON 内容或特定网络状态。先做离线替身验证，不要无限消耗第三方 API 费用。

## 目标设计：跨轮可追溯的任务状态

1. 新增可持久化、可版本化的 PendingCalendarIntent/ConversationTask 或等价结构：taskId、revision、用户消息证据 ID、每字段来源、创建时的可信时钟与时区、对象类型、数量、事件标题、时间窗口、重复模式、重叠约束、缺失字段、审核状态。注意它与正式草稿/正式事件不同。
2. 用户每轮纠正精确更新现有任务：“不用重复”覆盖周期规则；“就叫这个”补充标题；“确认”绑定当前唯一、有效、未过期的待确认任务，而不是当成日历文本重新解释。用户换话题或多任务冲突时禁止误绑定。
3. 聊天模型产出的 source/JSON 不是操作权威；从受信用户发言和被核对的模型建议建立任务快照。结构化生成收到的是经过验证的完整多轮任务状态，不只是最后几个字。
4. 模型提出的具体交叉时间只是建议，不能伪称用户明确给出；完整候选仍经过解析验证与可视化审查。
5. “确认”可完成信息收集并触发审查卡，但不自动等价于卡片审批或正式写入。发布必须保留明确授权、事务提交收据、版本冲突防护及幂等执行。
6. 显式用户创建要求应自动显示提案；“从此消息创建事件草稿”仅为备用操作。区分聊天回复、意图完成、提案生成、草稿持久化、用户授权、正式发布和失败阶段。
7. 相同标题允许多个事件。跨午夜时相对日期固定在原请求的时间锚点，不得将确认时日期当作“今天”。
8. 保存与纠错其他类型时同样维护上下文：用户说“这是个闹钟”“闹钟的 done 不是 memo 的 done”“这是 Deadline 不是 Memo”后，不应生成错误种类或在纠正时无意重复发布正式对象。历史屏幕中曾出现“正式发布 1”，但缺少完整授权与数据库记录，必须独立取证，不能直接断言越权。
9. 不能通过简单增加超时、无依据重试、无授权付费调用或加入 Function Calling 而绕过任务状态问题。Function Calling 不是实现此功能的必要前提。

## 必须新建的回归验收

- MT-01：完整重放上述逐轮输入，最终恰好产生五个同名、单次、窗口内有重叠的候选卡。
- MT-02：“确认”传给结构化端的是完整任务快照，而不是仅“确认”一词。
- MT-03：在 23:59 开始请求、过午夜才确认，仍按开始时的“今天”解释；时区/DST 另测。
- MT-04：用户纠正“重复→多个一次性”后不能出现 RRULE。
- MT-05：多次确认、网络重试、重启及重复点击不会重复创建或发布。
- MT-06：没有明确审查卡授权时，formal event count、commit receipt 不变化。
- MT-07：授权一次后五个 eventSeq 均独立、数据库与 UI/重启保持一致。
- MT-08：同名标题不被合并；更换话题或另一任务不串话；类型纠错不多次正式写入。
- MT-09：恶意/错误模型 source、示例占位文案和上传文件内容不能篡改受信任务。
- MT-10：真实缺失字段、模型空 JSON、HTTP 503、超时必须报出准确原因，不要谎称用户从未提供信息。
- MT-11：先使用固定 Clock 与伪模型离线重现 FAIL→PASS，再在许可条件下最少次数的免费 provider 真实 Android UI 复测。
- MT-12：输出独立测试日志、截图、数据库事务证据与结案报告；维持冻结 HOLD，直到该功能真实签核。
