# Skin Studio AI Automation Interface v1

Status: **implemented for `.pcskin` v3 inspection, editing, building, validation and static Bridge v1 action auditing**.
This interface makes source, assets, `project.json`, and package metadata callable by
scripts and agents. It does not claim complete visual Studio editing or Native/Skin
functional parity.

The machine-readable Host protocol is defined in
[`contracts/web-skin-bridge-v1.schema.json`](contracts/web-skin-bridge-v1.schema.json).
It describes both `action` and `command` envelopes. Host decoders remain the runtime
authority; JVM regressions submit each schema example to the actual decoder.

## Entry point and output contract

Run commands from the repository root with Python 3:

```powershell
python tools/skin-studio/skin_studio.py inspect-v3 path\to\skin.pcskin
python tools/skin-studio/skin_studio.py analyze-v3 path\to\skin.pcskin
python tools/skin-studio/skin_studio.py audit-bridge-v3 path\to\skin.pcskin
python tools/skin-studio/skin_studio.py read-v3 --file path\to\skin.pcskin --path web\app.js
python tools/skin-studio/skin_studio.py edit-v3 --file path\to\skin.pcskin --operations operations.json --out path\to\skin-edited.pcskin
python tools/skin-studio/skin_studio.py build-v3 --manifest manifest.json --source-dir source --out path\to\skin-built.pcskin --json
python tools/skin-studio/skin_studio.py validate path\to\skin-edited.pcskin --json
```

`inspect-v3`, `analyze-v3`, `read-v3`, and `edit-v3` emit one UTF-8 JSON object on stdout. Their
errors emit a JSON object on stderr and return exit code 2. A successful `edit-v3`
returns package SHA-256, output path, resulting manifest, and before/after hashes for
every changed file. The input and output package paths must differ. Output creation is
exclusive: an existing destination is never overwritten; select a new path.

`build-v3 --json` and `validate --json` emit one UTF-8 JSON receipt on stdout. Build
receipts contain the output path, package SHA-256, byte and source-file counts, and the
validated manifest. Validation receipts contain package SHA-256, byte count, runtime
version, skin identity and version-specific file/scene/asset counts. Execution failures emit
`{"schemaVersion":1,"command":"…","ok":false,"error":"…"}` on stderr and return
exit code 2. `build-v3` validates and reimports its generated package before publishing
it, then atomically creates a new output path; it never overwrites an existing file.
Without `--json`, successful build/validate commands retain their human-readable output.

## Static page and component inventory

Use `analyze-v3 <skin.pcskin>` after inspection to enumerate packaged `.html` / `.htm`
pages and their explicitly nested source elements. The UTF-8 JSON receipt contains the
package hash, per-page source hash and title, stylesheet/script references, component
count, and a preorder component index. Each component has a package-local `nodeId`,
`parentId` / `childIds`, tag, source line/column, full ordered attributes, optional `id`
and `data-component`, and bounded direct text. `interactiveCount` counts native control
tags, recognized roles and `data-action` / `data-local` controls. Duplicate HTML IDs and
unmatched or unclosed tags are reported as warnings.

The inventory is a **static source index**, not a browser DOM: JavaScript is not run,
computed styles are not resolved, and components generated by scripts or implicit
HTML5 tree-repair rules may not appear with runtime structure. `nodeId` is only stable
for the same page source/order; recalculate it after edits and use the source/package
hashes as the concurrency snapshot. Read linked scripts and styles with `read-v3` before
editing. The command does not modify or normalize package bytes.

## Static Host Bridge v1 action audit

Run `audit-bridge-v3 <skin.pcskin>` on a built or edited package. It indexes literal
`data-action` attributes in packaged `web/*.html` and `web/*.htm`, checks each action
name against the closed Bridge v1 decoder registry, and checks that a package declaring
static actions also requests `host.action`. A regression test compares the checked-in
registry to `WebSkinHost.decodeBridgeAction`, so runtime action changes fail the Studio
test suite until the registry is updated.

The UTF-8 JSON receipt includes the package hash, known bindings with page and static
node IDs, unknown bindings, declared/required/missing capabilities, the audit scope,
`requiresSourceReview`, the schema path/hash and a `payloadSchemaRef` for each known
binding. Follow that reference into the protocol schema when checking how the calling
script must construct its payload. A successful audit writes JSON to stdout and exits 0.
Unknown actions, a missing required capability, or an input/schema error writes
structured JSON to stderr and exits 2. The audit does not modify the package.

This is a **static-name and manifest-declaration check only**. It does not execute
JavaScript, discover runtime-created controls, validate payload fields, or prove Android
Host behavior. Packages with linked or inline scripts set `requiresSourceReview`; inspect
those scripts and [`V3_HOST_BRIDGE_EXTENSION.md`](V3_HOST_BRIDGE_EXTENSION.md) before
export. The referenced schema is exercised against Host decoders with representative
valid examples, required-field omissions and unknown-field mutations; it is not a JS
source analyzer. A passing receipt is not full Bridge compatibility or runtime-parity
evidence.

## Inspection and source reads

`inspect-v3` first validates the complete package using the production v3 validator.
Its response contains:

- `manifest` and `manifestSha256` (the SHA-256 of canonical UTF-8 JSON with sorted
  keys and compact separators);
- the full parsed `project.json` object, so agents can inspect and query its structure;
- package and inflated sizes; and
- a path-sorted file index with size, SHA-256, and UTF-8/binary classification.

Use `read-v3 --file <skin> --path <package-path>` to read one file. Recognized source
extensions return UTF-8 text when valid; binary/unknown extensions and invalid UTF-8
return Base64. This is extension-based because arbitrary binary data can itself happen
to form valid UTF-8. Each response contains exact byte count and SHA-256. Paths are
package-relative POSIX paths under `web/` or `assets/`, or the root `project.json`.

## Transactional edit document

The operation file is UTF-8 JSON with exactly one top-level field:

```json
{
  "operations": [
    {
      "op": "write",
      "path": "web/custom.css",
      "encoding": "utf-8",
      "content": ".card { border-radius: 18px; }\n",
      "expectedAbsent": true
    }
  ]
}
```

An operation batch contains 1–128 operations. It is applied to an in-memory package,
then the **entire final package** is validated and built with `runtime_package_v3` before
any output is created. A failure leaves the input package unchanged and creates no
output package. The final archive retains the existing v3 size, path, resource, remote
URL, capability and manifest validation rules.

Supported operations:

| Operation | Fields and behavior |
|---|---|
| `write` | `path`, `encoding` (`utf-8` or `base64`), `content`, and exactly one guard: `expectedSha256` for replacing an existing file, or `expectedAbsent: true` for creating a new file. |
| `delete` | `path` and the file's `expectedSha256`. Required runtime files cannot be deleted. |
| `move` | `from`, unused `to`, and source `expectedSha256`; package references are not rewritten automatically. |
| `component-insert` | `path`, current HTML `expectedSha256`, `targetNodeId` from `analyze-v3`, `position` (`before`, `after`, `prepend`, `append`), and a balanced HTML `html` fragment. |
| `component-remove` | `path`, current HTML `expectedSha256`, and `targetNodeId`; `html`, `head`, and `body` document shells are protected. |
| `component-replace` | `path`, current HTML `expectedSha256`, `targetNodeId`, and a balanced replacement fragment. |
| `component-move` | `path`, current HTML `expectedSha256`, `sourceNodeId`, `targetNodeId`, and `position`; the source and destination are in the same page. Moving a node into itself or a descendant is rejected. |
| `json-patch` | `path: "project.json"`, current file `expectedSha256`, and a JSON Patch list. Supported ops are `add`, `remove`, `replace`, `move`, `copy`, and `test`; paths use RFC 6901 JSON Pointers. |
| `manifest-patch` | current `expectedSha256` from `inspect-v3`, and JSON Patch ops. `format`, `schemaVersion`, `entrypoint`, `project`, and `sha256` are managed and cannot be changed. Changing `capabilities` additionally requires `allowCapabilityChange: true`; the package is still subject to Android Host capability enforcement. |

Each edit has a SHA precondition to reject stale work. When applying multiple changes
to one JSON file, combine them in one `json-patch` operation. Filesystem names are
validated; traversal, absolute paths, backslashes, and `manifest.json` writes are
rejected. Limits are 128 package operations, 256 JSON Patch operations per JSON file,
96 package source files, 600 KB per text file, 3 MB per binary file, and the v3 archive
limits enforced by the production validator.

Component operations address the explicit, balanced source tree reported by
`analyze-v3`; they do not execute JavaScript or edit computed browser DOM. Re-run
`analyze-v3` and use the current HTML file hash after each source-changing operation,
because `nodeId` includes the source order. The editor refuses malformed pages/fragments,
new duplicate HTML IDs, mutations of the `html`/`head`/`body` shell, and HTML insertion
inside raw-text elements such as `script` and `style`. Runtime-created controls remain
editable through ordinary source `write` operations. The operations preserve all bytes
outside the selected source range and validate/rebuild the complete v3 package before
publishing an output file.

## Browser Studio structure editor

The local browser Studio uses the same v3 source model and the same static inventory and
component operations. `POST /api/analyze-v3` accepts `{ "manifest": ..., "files": ... }`,
where each file value is Base64, validates the project with the production v3 builder, and
returns the `analyze-v3` receipt. `POST /api/edit-components-v3` accepts those fields plus
one `operation` from the table below; it returns changed source files as Base64, before/after
hash receipts, and a fresh analysis. Stale page hashes and invalid structures return HTTP
400 without changing the browser project's source map.

In the Studio, the **HTML 结构树** panel selects a packaged HTML page and supports source
fragment insertion before/after/inside a selected node, replacement, deletion, and moving
the selected node relative to a target. Each accepted edit updates the same in-memory source
bytes used by the source editor, live package preview, project save and `.pcskin` export.
The tree is a static source inventory: JavaScript-generated nodes remain available through
the advanced source editor. This structural panel does not yet provide a full CSS layout,
computed-style, interaction-logic or accessibility editor.

Clear's month page uses source-editable `selectMonth`, `selectMonthDate`, and `todayInMonth`
Host actions for year/month navigation and local-date selection. The Studio's action catalog
and preview Mock recognize these bindings. `selectMonth` carries a canonical `YYYY-MM`,
`selectMonthDate` carries an ISO date within the displayed month, and `todayInMonth` has no
extra fields. They update only Host month-selection state; use `jumpTimelineDay` for the
separate action that opens the selected day on the Timeline. Month agenda cards preserve a
projected repeating event's `originalOccurrenceKey`; the Host revalidates it before opening
the existing scoped editor. Clear renders selected/today dates in the Host-projected zone,
including when the UTC date differs. See
[`V3_HOST_BRIDGE_EXTENSION.md`](V3_HOST_BRIDGE_EXTENSION.md) for the closed schemas and
validation behavior. The Mock is non-writing and is not Android WebView evidence.

Example: insert a component under an analyzed container. `targetNodeId` and the page
hash come from the same `analyze-v3` / `inspect-v3` snapshot:

```json
{
  "operations": [{
    "op": "component-insert",
    "path": "web/index.html",
    "expectedSha256": "<current-page-sha256>",
    "targetNodeId": "web/index.html#n00012",
    "position": "append",
    "html": "<section id=\"custom-panel\"><h2>自定义</h2></section>"
  }]
}
```

## Agent workflow

1. Run `inspect-v3` and keep its `packageSha256`, file hashes, and `manifestSha256` as
   the revision snapshot; run `analyze-v3` to locate static HTML pages and controls.
2. Run `read-v3` for each source or binary asset that needs inspection. Decode binary
   files only when needed; preserve their bytes if they are not being changed.
3. Construct a bounded operation JSON. Use component operations for precise edits to
   analyzed static HTML nodes; use guarded source writes for JavaScript-generated DOM,
   CSS, scripts and arbitrary source; use JSON Patch for `project.json` metadata and
   Base64 writes for binary assets.
4. Run `edit-v3` to a **new** output path. A stale guard or invalid final package
   returns a structured error and does not create the output.
5. For source-directory projects, run `build-v3 --json` to create a validated package;
   for edited packages, run `validate --json` on the exported `.pcskin`. Both return
   hashes and counts; build refuses an existing output path.
6. Run `audit-bridge-v3` on the resulting package. Resolve unknown static action names
   and missing capability declarations; inspect linked/inline scripts when requested.
7. Inspect/read the result again and compare intended
   changes and hashes. Use the Studio browser preview and Android WebView/device
   acceptance for visual and runtime claims.

## Executable end-to-end authoring example

The regression `tools/skin-studio/tests/test_ai_skin_workflow_v3.py` runs the documented
machine interface against the canonical Clear source without modifying the bundled APK
asset. It builds an isolated `.pcskin`, reads machine receipts to locate `#app` and the
stylesheet hash, inserts a static component, updates CSS with its SHA guard, validates the
new package, then re-inspects and checks that only the intended HTML/CSS files changed and
the Host capability declaration stayed identical. Run it with:

```powershell
python -m unittest discover -s tools/skin-studio/tests -p test_ai_skin_workflow_v3.py -v
```

This exercises the documented tool workflow, not a model's design quality or an Android
runtime result. The browser E2E and device checks remain separate evidence.

The interface enables arbitrary v3 source/asset file CRUD, generic JSON tree edits, and
guarded structural edits to explicit static HTML elements; it does not impose a formal
page/component schema on `project.json`, nor does it inspect script-generated runtime
DOM. The browser Studio now exposes the static HTML component tree described above, in
addition to direct project JSON editing, supported UTF-8 file creation/deletion, and
arbitrary asset add/replace/delete with text-reference guards. CSS layout, computed browser
state, JavaScript-generated nodes and Bridge behavior remain source-edited rather than
semantically modeled. Host capabilities remain requests declared by the skin and never
constitute user approval. Browser Mocks and successful package validation do not prove
Android behavior, device compatibility, or Core/Host/Skin parity. Full visual authoring,
Host Bridge parity, default-skin cutover, and physical-device acceptance remain separate
open work.
